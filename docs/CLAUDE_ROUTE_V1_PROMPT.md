### 後補流程圖核對

使用者補上標題為「矮人礦坑（優化版）遊戲流程圖」的圖片，補齊 PDF 第 7 頁所提的流程圖。圖中的主要流程與文字檔一致：

1. 開始探勘起算整局 300 秒、coins=0；抽地圖後 16 張重洗，抽到 5 張道路牌，初始 R 加在第一段 a。
2. 每次回到目前路段先檢查：牌庫空且手牌付不出鋪路／硬挖才失敗；否則玩家選鋪路、硬挖或換牌。

5. 通過末段不補牌，直接翻終點；金幣 coins+1 後回到抽地圖／重洗流程，金礦立即結算。
6. 圖底仍寫「金礦 > 牌用盡 > 超時」；**這不授權已到期的新行動繼續結算**。截止前接受並完成的行動內，末段到達金礦先於牌空判定；滿 300 秒送達的新行動先超時。以本節使用者確認為準。

## 必須忠實實作的規則

完整規則以 `ROUTE_V1_SPEC.md` 為準，以下列出最容易誤用舊引擎的部分。

- 新牌庫 H4/V4/B2/X1/R5，共 16；每張地圖都重建、重洗全部 16 張，不是拿上一張剩餘牌繼續。
- 開局抽到手上 5 張道路牌才停止。R 立即移出、第一段 `a++`、繼續抽；因此開局剩餘牌數不是固定 11，而是 `16-5-r0`。
- 三種地圖每次各 1/3 獨立抽，可重複。`mapIndex` 是本局第幾張（1..3），`mapId` 是抽到哪種（1..3），兩者不得混用。
- 地圖一：first HH；A=B→HV→V；B=HH→HV。
- 地圖二：first HV；A=B→HH→H；B=VV→H→H。
- 地圖三：first B；A=HH→VV→V；B=VV→B→VV。
- 付款是 H/V/B/X 的張數組合，不是手牌 index＋格子座標。鋪路須剛好付 `sum(need)+a` 張，且 `Σ max(0,need[t]-pay[t]) <= pay.X`；十字每張只補一個缺口，其餘付牌可當任意成本。
- 硬挖剛好付 `3+a` 張任意道路牌，即使能鋪路也仍是合法選項。不能只保留看似便宜的一種付法或排除「浪費十字」的付法。
- 換牌只在牌庫非空時合法，棄一張道路牌，再抽到一張道路牌或牌庫空；其中每張 R 都加在現在的 `a`。
- 通過路段後先前進、`a=0`，再補到上限；新抽落石加在**新的位置**。岔路處也先補牌、累積 a，再讓玩家看牌選 A/B，a 帶入所選第一段。選岔路不增加動作數，選後不能回頭。
- 通過最後一段：不補牌，立即揭終點。C→coins+1、重抽地圖重洗新牌；G→60+20×coins 結束。
- 金礦所在的地圖序號等機率為 1／2／3，等價條件機率 1/3、1/2、1；不是每張重新獨立擲 1/3，也不是三種 mapId 各玩一次。
- 任一圖失敗整局 0 分，不能把已得金幣先永久保存成分數。
- 牌庫空仍可付牌繼續；只有當前位置已無鋪路／硬挖可做且不能換牌時才失敗。不能用「牌庫空」或「手牌不足上限」直接判輸。
- 採嚴格 300 秒截止，所有新行動先由伺服器單一時間點判定是否到期；GET 恢復、lifecycle、提前結束同樣不能覆蓋已到期的 timeout。逾時 endedAt 保持 deadlineAt，不改成重開頁面時刻。理論精算仍依原文忽略時間與放棄。
- 玩家可選任何合法動作，遊戲引擎不得強制走最佳策略；最佳策略僅用於理論分析與提示。

## 精確分析器

### 計算方法與驗證

- 使用記憶化的狀態遞迴／MDP 逆向歸納，`draw`、`best` 與所有動作 Q 值均用 BigInt 有理數；正分母、約分、比較交叉相乘，不能轉浮點比較後決定最佳動作。
- 狀態至少包括 configId、mapId、pos（含岔路）、a、手牌 4 元組、牌庫 5 元組，draw 另含還要抽幾張道路牌。cache 不可跨設定誤用。
- 抽牌每一支權重為剩餘張數／總數。R 不減少待抽道路數，會令 a+1；道路牌入手並令待抽數-1。分支和須精確為 1。
- `best` 取所有合法動作的通關率最大值；無合法動作為 0，終點為 1。岔路在補完牌後才 max(A,B)，不能提前看到牌再以錯誤時點選路。
- 全程保留原文平手規則；期望動作數跟著同一最優通關策略遞迴，不能另行最小化動作數。鋪路／硬挖／換牌各加 1、選岔路不加。
- 某狀態理論通關率為 0，不代表遊戲當下已符合失敗條件。只要牌庫仍有牌、尚能換牌，就須照規則與固定平手策略繼續計算動作數；不能因成功率剪枝而把剩餘動作數直接設成 0。
- 理論分析忽略超時／放棄，必須在結果標示。對真人資料不可宣稱忽略時間後的理論值就是含 300 秒的保證。
- `p=(p1+p2+p3)/3`；PMF：p/3、p²/3、p³/3，0 分為其餘；再以**未捨入分數**推導 CDF、E[X]、E[X²]、Var(X) 與 P(S)。
- 每張地圖的期望動作數為無條件期望（含失敗），整局用平均值×`(1+2p/3+p²/3)`。不要只平均成功局。
- 可參數化落石張數、手牌上限、固定 A/B、禁止硬挖、路段需求；PDF 另列道路牌數、硬挖基礎成本、得分參數，請把計算核心設計成可擴充。
- 結構合法性與設計目標分開：落石 4 張的比較情境刻意超出設計目標，也必須能計算。改參數後要重算，不能拿基準表直接代用。
- 若支援金礦分為 0 等 PDF 可調範圍，通關事件仍依「挖到金礦」，不能一律用 `X>0` 代表；相同得分支點應合併。基準 60/20 才有原表的四個不同得分及 `S={X>0}`。

### 輸出

提供可執行 CLI（例如 `node tools/route-version/cli.mjs --scenario base --format json`），附實際可用命令，不只範例。輸出：

- 規則版本、完整參數快照／configId、`source: exact_dp`、p1/p2/p3、p。
- PMF/CDF、E、E2、Var、P(S)、各圖與整局期望動作數。
- 分數的 JSON 介面統一為 `{ numerator: "整數字串", denominator: "正整數字串", decimal: "顯示字串" }`；BigInt 不能直接 JSON.stringify，也不能先 Number 化再冒充精確分數。
- 狀態數、快取命中、實際計算時間及其他必要重現資訊。未完成／超過資源限制要明確回報，不准自動改用模擬並回傳相同的 exact_dp 標籤。
- 另可產生前端可載入的唯讀分析資料，版本／參數可核對，數值皆由程式計算；不得硬編碼參考表當作求解器。

### 必須重現的數值

`ROUTE_V1_SPEC.md` 第三節 A～D **全部**納入測試：兩個舊版回歸、三圖基準、6 種比較情境、所有 PMF／動差及超幾何檢查。精確項用有理數相等；動作數才依規格允許 ±0.01。關鍵基準：

```
p2 = 4577077/7567560
p3 = 17995499/30270240
p  = 125831/206388
E  = 195563555582424095/6593478448952304
Var= 60876528786036948852862724619816575/43473958056798480504795266908416
```

已由 Codex 作過**代數核對**：用給定 p_i 可得到原文全部平均 p 與基準 PMF/E/Var，各比較情境的 E/Var/P(S) 四捨五入值也一致。這僅證明表內算術一致，尚未證明 p_i 真的由上述狀態轉移產生；你的求解器必須獨立算出它們。

蒙地卡羅只作獨立驗證：明示 seed、局數、區間及模擬 PMF，實際依最佳策略發牌；不直接用理論 PMF 抽一個分數充當遊戲模擬。照規格做 100,000 局以上／各圖 200,000 次的驗證。95% 區間本身有機會不含真值，不能為過測試挑種子或隱藏偏差；有偏差先檢查規則與策略。精確等式測試才是核心驗收。

## API 契約：先提供給 Codex 銜接

### 過渡相容

- 現有前端仍呼叫舊 `place/discard`。新路段版可先用 `POST /api/games { deviceType, ruleset: "route-v1" }` 明確建局；前端正式切換前，保留舊請求的相容流程。

- 建局冪等雜湊要包括 ruleset 與伺服器選定配置識別。正式玩家不能藉建局 payload 任意改牌庫或分數。

### 行動與錯誤

- 保留 `POST /api/games/:id/actions`、`actionId`、`expectedRevision`，新 type 建議 `pave / dig / exchange / choose_branch / abandon`。
- pave/dig 帶完整 pay 4 元組；exchange 帶棄哪一種；choose_branch 帶 A/B。pay 必須是非負整數、不可超出手牌、不可多付／少付或虛構 R。
- `turn`／動作數只算前三種；選岔路仍是要冪等／revision+1 的玩家決策與事件，不能因不算回合就漏記。
- 自動補牌、連續 R、換地圖／發新手牌都在這次行動內原子完成；斷線重試不能再次抽地圖、抽牌或翻終點。
- 409 REVISION_CONFLICT／GAME_IN_PROGRESS 仍附最新安全 game，非法動作不消耗牌／次數／revision。保留現有玩家 cookie 隔離、同源與既有 lifecycle eventId 去重。
- 維持已修好的並發模式：讀完 body 後再讀遊戲；讀／驗證／寫入間不可插入 await 造成過期狀態覆蓋。精確求解不能塞在狀態交易中長時間運算。
- 遊戲狀態、事件與冪等回應同一 DB 交易寫入；回應送失後原 key 能重放相同結果。
- 已在截止前確認的同一 actionId，即使截止後重送，也重放原結果；這是已完成行動的查詢／重試，不能誤當新的到期行動改判或重執行。

### effects 與提示

- 白名單化 map_start、實際 draw、rock（a 增加）、pay、advance、fork_ready、choose_branch、reveal、map_end、end 等事件；具體名稱與安全欄位列進 API。
- 新 rock 是當前路段加成本，沒有 removed 道路、沒有 unreveal。到終點不再補牌或產生後續 rock。
- 最終 game 永遠是權威；effects 只給 Codex 做已確認結果的順序呈現，不讓前端重新執行亂數。
- 提示提供該局目前安全狀態的每個合法動作 Q 值、最佳標記與 tieRank；語意為「做完這個動作後，其餘採最佳策略的本張地圖通關率」，不含時間，不是整局金礦機率。
- 建議唯讀 `GET /api/games/:id/hints`（需該玩家 session），回帶 revision/version/configId，讓前端丟棄過時提示。讀取本身不增加動作數、不暫停時間；實際按提示按鈕的使用紀錄需另定 event 去重，不能把一次讀取算一次遊戲行動。
- 另提供 config 對應的唯讀精確分析結果，明示來源及完整參數。路由與快取策略先列入契約，不把個人 session 藏進公共快取。
- 使用預計算／快取或 Node 內建 Worker 執行重運算，避免精算長時間卡住 HTTP 主事件迴圈；未完成時回應明確狀態，不能讓遊戲行動或倒數同步被運算堵住。

## 持久化、統計與 CSV

- 延續規則版本、playerId、attempt、source/mode、時間點（epoch ms）、decisionMs、durationMs、reason、事件 seq、turn。
- 新增 mapIndex/mapId/position/branch/a、pay、動作前手牌／牌庫組成、實際抽牌（含 R），以及 configId／配置快照；可用遷移增加結構欄位或事件 payload，但 CSV 必須能匯出分析所需欄位，不能只藏在 state_json。
- 既有 `games.gold_row NOT NULL` 是舊格子世界的欄位。不要把「金礦在第幾張地圖」硬塞成舊 gold_row 的新含義；設計可回讀舊紀錄的新結構並測遷移。
- 遷移使用測試資料庫驗證舊 games/events 完整保留、新舊 CSV 皆可讀；不刪實際資料、不得重標舊版為新規則。
- mapIndex 是同一 game 內的進度，不可把通過幾張地圖混算成幾局；期望每局約 5.98 次動作也不能解讀成 5.98 張地圖。
- 統計／匯出可依規則版本／配置篩選，真人與計算／驗證模擬完全分開。基準理論整局成功率約 40.27%，單張地圖約 60.97%，不得把兩者比較錯。
- 依使用者已確認政策，既有 games/stats/CSV **仍公開讀取，不重加登入**。本輪只做 CLI 參數比較及唯讀結果，不新增網頁參數編輯或配置寫入 API。
- 正式變更配置須新版本／新快照；不得在同一局中途更改。設計目標 pi≤0.65、P(S) 40%～60% 是建議評估，不是要把試算結果裁切進區間。
