# 規則：三地圖路段版（route-v1，引擎 0.4.0）

2026-11-18 起的新規則。完整原文與參考數值見 `docs/ROUTE_V1_SPEC.md`；本檔記錄**實作採用的確切規則與決定**。舊格子版（`ruleset: grid`，0.3.1）的規則仍見 `docs/RULES.md`，兩者並存，資料以 `ruleset`／`version`／`configId` 分開。

單一來源：`shared/route-config.js`（地圖與參數）、`shared/route-engine.js`（遊戲）、`shared/route-analysis.js`（精算）。前端、後端、CLI 都 import 同一份，不各自抄規則。

## 牌與地圖

- 牌庫 H4 V4 B2 X1 R5（16 張）。**每張地圖開始時 16 張全部重建重洗**，不沿用上一張的剩牌；換圖時手牌也清空。
- 三種地圖每次各 1/3、獨立、可重複。`mapIndex`＝本局第幾張（1..3），`mapId`＝抽到哪一種（1..3），兩者不同。
  - 地圖一：HH → 岔路 → A：B→HV→V／B：HH→HV（**正式版用文字檔基準 HH→HV**；HV→HV 只是 CLI 比較情境 `map1BHVHV`）
  - 地圖二：HV → 岔路 → A：B→HH→H／B：VV→H→H
  - 地圖三：B → 岔路 → A：HH→VV→V／B：VV→B→VV
- 金礦位置：開局時以 1/3 均勻決定在第 1、2、3 張地圖（等價於條件機率 1/3、1/2、1）。不是每張重新擲 1/3。

## 流程

1. 開局發牌：依序抽到手上 5 張道路牌為止；每張落石翻開移出、第一段 `a+1`、繼續抽。開局後牌庫剩 `16-5-r0`。
2. 每回合在目前路段選一個動作（`turn`、`mapActionCount` +1）：
   - **鋪路 pave**：交出剛好 `need總數+a` 張，且 `Σ max(0, need[t]-pay[t]) ≤ pay.X`。十字每張補一個缺口，其餘付牌可當任意成本。每種不同的 `pay=(H,V,B,X)` 組合都是不同動作。
   - **硬挖 dig**：交出剛好 `3+a` 張任意道路牌。能鋪路時也可以硬挖。
   - **換牌 exchange**：牌庫非空才可。棄一張，抽到一張道路牌或牌庫空為止，落石加在**目前**位置。
3. 通過非末段：前進、`a=0`，補到 5 張；補牌抽到的落石加在**新位置**。新位置是岔路時，補完牌（落石累積在 a）後才選 A/B，a 帶入所選線第一段。**選岔路不算動作**（turn 不加），但仍是要冪等、revision+1、記事件的玩家決策；選了不能回頭。
4. 通過末段：**不補牌**，直接翻終點。金幣→coins+1、重抽地圖、重洗新牌；金礦→`60+20×coins` 結束。
5. 失敗：只有「牌庫空，且手牌既付不出鋪路也付不出硬挖」。牌庫空但仍付得出就繼續；任一張地圖失敗整局 0 分（金幣不先存成分數）。
6. 玩家可選任何合法動作，引擎不強制最佳策略。

## 時間（使用者 2026-11-18 確認：嚴格截止）

- `deadlineAt = startedAt + 300000`，伺服器時間為準，背景／關頁不暫停，換圖不重設。
- 新行動在 `serverNow >= deadlineAt` 時先結算 `timeout`（0 分、`endedAt = deadlineAt`），不付款、不抽牌、不翻終點。`deadlineAt - 1ms` 送達的合法末步仍可拿金礦。
- 截止前已確認的 `actionId` 在截止後重送：重放原結果（查詢已完成的行動），不改判。
- GET current、lifecycle、提前結束同樣先判逾時，不會覆蓋已到期的 timeout；截止前已確認的金礦也不會被之後的逾時覆寫。
- 同一個被接受的行動內：末段到金礦先於牌空判定（金礦 > 牌用盡）。流程圖底部的「金礦 > 牌用盡 > 超時」不授權已到期的新行動繼續結算。

## 精確分析的平手規則（使用者 2026-11-18 已確認）

原文「依 pay 字典序列舉鋪路／硬挖」沒有說清楚是「先列完鋪路再列硬挖」還是「兩種合併後依 pay 排序」。兩者的通關率完全相同（平手規則不影響 max），但期望動作數不同：

| 排序 | 地圖一 | 地圖二 | 地圖三 | 每圖平均 | 每局 |
| --- | --- | --- | --- | --- | --- |
| **合併依 pay 字典序（採用，`mergedByPay`）** | 4.0217 | 4.0444 | **3.6589** | 3.9083 | 5.9811 |
| 先鋪路後硬挖（`paveThenDig`） | 4.0217 | 4.0444 | 3.7063 | 3.9241 | 6.0053 |

只有 `mergedByPay` 重現規格參考值，因此採用；同一 pay 同時可鋪路與硬挖時，鋪路排在前（兩者結果狀態相同，動作數也相同）。換牌排在所有付牌之後，依棄 H、V、B、X。只有嚴格大於才替換；岔路平手選 A。CLI 可用 `--tie-order paveThenDig` 重現另一種結果。

使用者已明確選擇「採 mergedByPay，符合文件數值」；這不是仍待確認的暫行排序。前端切換政策也已確認：既有進行中的 grid 局須由玩家明確結束後才能開始 route-v1，不自動結束或刪除舊局。

理論分析忽略超時與放棄；不得把它當成含 300 秒限制的真人保證。
